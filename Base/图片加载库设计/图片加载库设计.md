# 图片加载库设计

## 一、整体架构

图片加载库的核心架构通常分为五层：

```
┌──────────────────────────────────────────────┐
│                  API 层                       │  对外暴露的接口（加载、取消、预加载等）
├──────────────────────────────────────────────┤
│               任务管理层                       │  管理加载任务的创建、调度、取消
├──────────────────────────────────────────────┤
│               缓存层                          │  内存缓存 + 磁盘缓存
├──────────────────────────────────────────────┤
│               下载层                          │  网络请求、数据下载
├──────────────────────────────────────────────┤
│               解码层                          │  图片解码、转换、压缩
└──────────────────────────────────────────────┘
```

## 二、核心模块设计

### 2.1 缓存模块

#### 2.1.1 内存缓存

- **数据结构**：使用 `NSCache` 作为内存缓存的底层实现
  - `NSCache` 是线程安全的，无需额外加锁
  - 系统内存不足时自动清理，遵循 LRU 淘汰策略
  - 支持设置 `countLimit` 和 `totalCostLimit` 控制缓存上限

- **弱引用辅助缓存**：
  - 使用 `NSMapTable` + `weak` 引用作为二级缓存
  - 当 `NSCache` 释放后，弱引用缓存仍可能命中，减少磁盘 I/O
  - key: URL 字符串，value: UIImage 的 weak 引用

```objc
@interface SDMemoryCache : NSObject
@property (nonatomic, strong, nonnull) NSCache<id, id> *cache;
@property (nonatomic, strong, nonnull) NSMapTable<id, id> *weakCache; // weak ref cache
- (nullable id)objectForKey:(nonnull id)key;
- (void)setObject:(nullable id)object forKey:(nonnull id)key;
- (void)setObject:(nullable id)object forKey:(nonnull id)key cost:(NSUInteger)cost;
- (void)removeObjectForKey:(nonnull id)key;
- (void)removeAllObjects;
@end
```

#### 2.1.2 磁盘缓存

- **存储路径**：`Library/Caches/com.xxx.imageloader/`
- **文件命名**：对 URL 做 MD5 或 SHA256 哈希作为文件名
- **数据结构**：
  - 自定义文件存储：每个缓存项一个文件，通过哈希 URL 映射
  - SQLite 存储：将图片数据写入数据库，适合小图片、高频访问场景
- **清理策略**：
  - 按时间清理：超过指定天数的缓存删除
  - 按容量清理：总缓存超过上限时，按最后访问时间（LRU）删除
  - 按磁盘空间清理：磁盘剩余空间不足时触发紧急清理

```objc
@interface SDDiskCache : NSObject
@property (nonatomic, assign) NSUInteger maxSize;       // 最大缓存大小（字节）
@property (nonatomic, assign) NSUInteger maxAge;        // 最大缓存时间（秒）
- (nullable NSData *)dataForKey:(nonnull NSString *)key;
- (void)setData:(nonnull NSData *)data forKey:(nonnull NSString *)key;
- (void)removeDataForKey:(nonnull NSString *)key;
- (void)removeAllData;
- (NSUInteger)totalSize;
@end
```

### 2.2 下载模块

#### 2.2.1 下载器设计

```
┌─────────────────────────────────────────────────┐
│              SDWebImageDownloader                │
├─────────────────────────────────────────────────┤
│  URL => SDWebImageDownloadToken (1:1 映射)       │
│  同一 URL 不会重复创建下载任务                      │
├─────────────────────────────────────────────────┤
│  并发控制：                                       │
│  - maxConcurrentDownloads (默认 6)               │
│  - NSURLSession 配置 HTTPMaximumConnectionsPerHost│
├─────────────────────────────────────────────────┤
│  执行顺序策略：                                    │
│  - FIFO（默认）：先进先出，按添加顺序依次下载        │
│  - LIFO：后进先出，最新请求优先执行（列表滚动推荐）  │
│  - 通过 NSOperation 依赖链实现 LIFO               │
├─────────────────────────────────────────────────┤
│  优先级调度：                                     │
│  - HighPriority / LowPriority 选项               │
│  - 映射到 NSOperationQueuePriority               │
│  - 可与 FIFO/LIFO 组合使用                        │
└─────────────────────────────────────────────────┘
```

- **去重机制**：使用字典 `URL -> [completionBlock]` 管理，同一 URL 多个回调只发一次请求
- **并发控制**：`NSURLSession` + `NSOperationQueue`，通过 `maxConcurrentOperationCount` 控制
- **取消机制**：返回 `token` 对象，持有对 `NSURLSessionTask` 的弱引用，可随时取消

#### 2.2.2 FIFO vs LIFO 加载策略

##### 核心概念

| 策略 | 全称 | 含义 | 适用场景 |
|------|------|------|---------|
| FIFO | First In First Out | 先进先出，按请求顺序依次加载 | 预加载场景、顺序展示场景 |
| LIFO | Last In First Out | 后进先出，最新请求优先加载 | 列表快速滚动场景（推荐） |

##### 为什么列表滚动推荐 LIFO？

```
  用户快速向下滑动列表：
  ┌─────────────────────┐
  │  Item 1  (旧)  ← 已滚过，用户不再关注    │
  │  Item 2  (旧)  ← 已滚过                  │
  │  Item 3  (旧)  ← 已滚过                  │
  │  Item 4  (当前) ← 用户正在看这里！         │
  │  Item 5  (最新) ← 用户即将看到            │
  │  Item 6  (最新) ← 用户即将看到            │
  └─────────────────────┘

  FIFO 策略：Item 1 先下载 → Item 2 → Item 3 → Item 4 → Item 5 → Item 6
  ❌ 问题：用户已经滚过了 Item 1-3，下载完后用户看不到
  ❌ Item 4（用户正在看）要等 Item 1-3 下载完才能开始

  LIFO 策略：Item 6 先下载 → Item 5 → Item 4 → Item 3 → Item 2 → Item 1
  ✅ 优势：用户正在看和即将看到的图片优先加载
  ✅ 已滚过的旧图片延后加载，如果又被滚回来再下载也不迟
```

##### SDWebImage 的 LIFO 实现原理

SDWebImage 使用 **NSOperation 依赖链** 实现 LIFO，而不是简单调整优先级：

```objc
typedef NS_ENUM(NSInteger, SDWebImageDownloaderExecutionOrder) {
    SDWebImageDownloaderFIFOExecutionOrder,  // 默认：先进先出
    SDWebImageDownloaderLIFOExecutionOrder   // 后进先出
};

// SDWebImageDownloader 属性
@property (assign, nonatomic) SDWebImageDownloaderExecutionOrder executionOrder;
@property (weak, nonatomic, nullable) NSOperation *lastAddedOperation;  // 最近添加的 Operation
```

**核心实现代码**：

```objc
// 添加 Operation 到队列
[self.downloadQueue addOperation:operation];

// LIFO 模式：通过依赖链让旧 Operation 依赖新 Operation
if (self.executionOrder == SDWebImageDownloaderLIFOExecutionOrder) {
    // 让上一个 Operation 依赖当前新添加的 Operation
    // 效果：新 Operation 无依赖可立即执行，旧 Operation 必须等新 Operation 完成后才能执行
    [self.lastAddedOperation addDependency:operation];
    self.lastAddedOperation = operation;
}
```

**依赖链的工作过程**：

| 步骤 | 添加的 Operation | 依赖关系 | 执行顺序 |
|------|-----------------|---------|---------|
| 第 1 步 | Op-A 加入 | 无依赖 | Op-A 立即开始执行 |
| 第 2 步 | Op-B 加入 | `[Op-A addDependency:Op-B]` | Op-B 无依赖先执行 → Op-A 等 Op-B 完成后才执行 |
| 第 3 步 | Op-C 加入 | `[Op-B addDependency:Op-C]` | Op-C 无依赖先执行 → Op-B 等 Op-C → Op-A 等 Op-B |

```
  依赖链示意图（LIFO 模式）：

  Op-A ← addDependency:Op-B ← addDependency:Op-C

  等价于：Op-A 依赖 Op-B，Op-B 依赖 Op-C

  执行顺序：Op-C（无依赖，立即执行）→ Op-B → Op-A

  最终效果：最新添加的 Operation 最先执行，实现了后进先出！
```

**为什么用依赖链而不是优先级？**

```objc
// ❌ 仅调整优先级无法保证 LIFO
// NSOperationQueue 在同一优先级的 Operation 中仍是 FIFO 顺序
// 不同优先级之间也只是概率上的优先，不是绝对的先后顺序
operation.queuePriority = NSOperationQueuePriorityHigh;  // 不保证一定最先执行

// ✅ 依赖链是硬约束
// 依赖关系是绝对的：被依赖的 Operation 必须完成后，依赖它的 Operation 才能开始
// 这保证了 LIFO 的严格顺序
[lastAddedOperation addDependency:newOperation];  // 硬约束，新 Operation 必须先完成
```

##### FIFO vs LIFO 详细对比

| 维度 | FIFO | LIFO |
|------|------|------|
| 执行顺序 | 按添加顺序依次执行 | 最新添加的先执行 |
| 实现方式 | 默认 NSOperationQueue 行为 | NSOperation 依赖链反转 |
| 列表滚动体验 | 顶部图片先加载，当前位置图片延迟 | 当前位置图片先加载，体验更流畅 |
| 预加载场景 | ✅ 适合：预加载按顺序依次完成 | ❌ 不适合：预加载顺序被打乱 |
| 依赖链复杂度 | 无额外依赖，简单 | 串行依赖链，并发度受限 |
| 取消影响 | 取消不影响其他任务 | 取除中间 Operation 会断开依赖链 |
| 内存峰值 | 逐步加载，峰值可控 | 一次性加载多张新图片，峰值可能较高 |

##### LIFO 的局限性与优化

```
  局限性 1：依赖链导致并发度降低

  FIFO 模式：6 个 Operation 可以同时并发下载（maxConcurrent = 6）
  LIFO 模式：只有最新 Operation 可以执行，其余都在等待依赖完成
  → 实际并发数降为 1，下载吞吐量大幅下降！

  ✅ 优化方案：混合策略
  - 保留最近 N 个 Operation 不设依赖（允许并发）
  - 超过 N 的旧 Operation 依赖最新的一批
  - 既保证当前可见图片优先，又不完全牺牲并发度
```

```objc
// 混合策略实现：最近 3 个 Operation 可并发，更旧的串行等待
@property (nonatomic, strong) NSMutableArray<NSOperation *> *recentOperations; // 最近 N 个
@property (nonatomic, assign) NSInteger maxConcurrentRecentOperations; // 默认 3

- (void)addOperationWithMixedStrategy:(NSOperation *)operation {
    [self.downloadQueue addOperation:operation];

    if (self.recentOperations.count < self.maxConcurrentRecentOperations) {
        // 最近 N 个不设依赖，允许并发
        [self.recentOperations addObject:operation];
    } else {
        // 超过 N 个的旧 Operation 依赖最新的批次
        NSOperation *latestBatch = self.recentOperations.lastObject;
        [operation addDependency:latestBatch];
        // 更新 recentOperations：移除最旧的，加入新的
        [self.recentOperations removeObjectAtIndex:0];
        [self.recentObjects addObject:operation];
    }
}
```

```
  局限性 2：取消中间 Operation 断开依赖链

  依赖链：Op-A → Op-B → Op-C → Op-D
  取消 Op-C → Op-B 仍依赖 Op-C，但 Op-C 已取消
  → Op-B 永远无法执行（依赖已取消的 Operation）

  ✅ 优化方案：取消时重建依赖链
  当一个 Operation 被取消时，将其依赖关系转移给下一个 Operation
```

```objc
// 取消 Operation 时修复依赖链
- (void)cancelOperationAndFixDependency:(NSOperation *)operation {
    // 找到依赖 operation 的所有 Operation
    NSArray *dependents = [self allDependentsOfOperation:operation];

    // 找到 operation 依赖的 Operation（即 operation 之后加入的）
    NSArray *dependencies = operation.dependencies;

    // 转移依赖：让 dependents 直接依赖 dependencies
    for (NSOperation *dependent in dependents) {
        [dependent removeDependency:operation];
        for (NSOperation *dependency in dependencies) {
            [dependent addDependency:dependency];
        }
    }

    // 取消该 Operation
    [operation cancel];
}
```

##### 实际应用建议

| 场景 | 推荐策略 | 原因 |
|------|---------|------|
| 列表快速滚动（TableView/CollectionView） | LIFO | 当前可见区域优先加载 |
| 缓慢浏览 / 预加载下一页 | FIFO | 按顺序预加载，用户体验连贯 |
| 详情页单张大图 | FIFO 或 LIFO | 只有一个请求，策略无所谓 |
| 混合场景（列表 + 预加载） | LIFO + 混合策略 | 可见区域 LIFO 优先，预加载 FIFO 兜底 |

```objc
// 设置执行顺序
SDWebImageDownloader.sharedDownloader.executionOrder = SDWebImageDownloaderLIFOExecutionOrder;

// 滚动时使用 LIFO + LowPriority
- (void)scrollViewDidScroll:(UIScrollView *)scrollView {
    // 可见区域的图片用 LIFO 优先加载
}

// 滚动停止后切换为 FIFO + 预加载
- (void)scrollViewDidEndDecelerating:(UIScrollView *)scrollView {
    SDWebImageDownloader.sharedDownloader.executionOrder = SDWebImageDownloaderFIFOExecutionOrder;
    // 预加载上下各 5 行的图片
    [self preloadNearbyImages];
}
```

### 2.3 解码模块

#### 2.3.1 为什么需要解码

- **问题**：UIImageView 设置 image 时，如果图片未解码，会在主线程进行解码（隐式解码），导致卡顿
- **时机**：图片解码应在子线程提前完成，主线程只负责渲染

#### 2.3.2 解码流程

```
原始图片数据 (JPEG/PNG/WebP)
        │
        ▼
  ImageIO 解码（CGImageSourceCreateWithData）
        │
        ▼
  获取 CGImage
        │
        ▼
  创建 Bitmap Context（CGBitmapContextCreate）
        │
        ▼
  绘制到 Context（CGContextDrawImage）
        │
        ▼
  获取解码后的 CGImage（CGBitmapContextCreateImage）
        │
        ▼
  创建 UIImage（[UIImage imageWithCGImage:]）
```

#### 2.3.3 解码关键参数

```objc
// CGBitmapContextCreate 参数
size_t width = CGImageGetWidth(cgImage);
size_t height = CGImageGetHeight(cgImage);
// 使用 32 位 BGRA 格式，避免渲染时的像素格式转换
CGBitmapInfo bitmapInfo = kCGBitmapByteOrder32Host | kCGImageAlphaPremultipliedFirst;
CGColorSpaceRef colorSpace = CGColorSpaceCreateDeviceRGB();
CGContextRef context = CGBitmapContextCreate(NULL, width, height, 8, 0, colorSpace, bitmapInfo);
```

#### 2.3.4 特殊处理

- **降采样（Downsampling）**：大图加载时，只需显示缩略图大小，应降采样解码减少内存占用
  - 计算 `imageSize` 和 `targetSize` 的缩放比
  - 使用 `CGImageSourceCreateThumbnailAtIndex` 直接生成缩略图
- **渐进式解码**：JPEG/PNG 支持逐行解码，边下载边显示模糊图逐渐清晰
  - 使用 `CGImageSourceCreateIncremental` 创建增量源
  - 每收到一部分数据调用 `CGImageSourceUpdateData` 更新
  - 从 `CGImageSource` 创建当前已解码的图片

### 2.4 任务管理模块

#### 2.4.1 加载流程（核心流程）

```
 loadImageWithURL
        │
        ▼
 ┌─ 查找内存缓存 ──┐
 │  命中？         │
 │  ├─ YES ──── 返回图片
 │  └─ NO         │
 └────────────────┘
        │
        ▼
 ┌─ 查找磁盘缓存 ──┐
 │  命中？         │
 │  ├─ YES ──── 子线程解码 ── 写入内存缓存 ── 返回图片

        │
        ▼
 ┌─ 创建/复用下载任务 ──┐

```

#### 2.4.2 任务调度策略

- **优先级**：UI 可见的加载任务优先级高于预加载任务
- **取消策略**：cell 复用场景，滚动时取消不可见 cell 的下载任务
- **回调线程**：所有 completionBlock 回到主线程执行

## 三、多尺寸图片加载策略

### 3.1 问题背景

同一张图片在不同场景下需要不同尺寸：

| 场景 | 需要的尺寸 | 典型尺寸 | 内存占用 |
|------|-----------|---------|---------|
| 列表缩略图 | 小 | 60×60 | ~14 KB |
| 详情页头图 | 中 | 375×375 | ~562 KB |
| 全屏大图 / 横屏壁纸 | 大 | 1242×2208 | ~10.7 MB |
| 原图上传 / 编辑 | 原始 | 4000×3000 | ~48 MB |

**核心矛盾**：如果只缓存原图，列表缩略图占 48 MB 内存只为显示 60×60 像素；如果只缓存缩略图尺寸，详情页需要重新下载原图。

### 3.2 多尺寸缓存 key 设计

#### 3.2.1 缓存 key 的构成

```
缓存 key = URL + 尺寸参数 + 变换参数

示例：
  原图缓存 key:    "https://img.example.com/photo.jpg"
  缩略图缓存 key:  "https://img.example.com/photo.jpg{w60_h60}"
  中等尺寸缓存 key: "https://img.example.com/photo.jpg{w375_h375}"
  圆角缩略图 key:   "https://img.example.com/photo.jpg{w60_h60_r10}"
```

```objc
@interface SDImageCacheKeyGenerator : NSObject
// 生成缓存 key
- (nonnull NSString *)cacheKeyForURL:(nonnull NSURL *)url
                          context:(nullable SDWebImageContext *)context;

// 具体实现
- (NSString *)cacheKeyForURL:(NSURL *)url context:(SDWebImageContext *)context {
    NSString *key = url.absoluteString;

    // 附加尺寸信息
    CGSize targetSize = [context[SDWebImageContextImageThumbnailPixelSize] CGSizeValue];
    if (!CGSizeEqualToSize(targetSize, CGSizeZero)) {
        key = [key stringByAppendingFormat:@"{w%d_h%d}", (int)targetSize.width, (int)targetSize.height)];
    }

    // 附加变换信息
    id transformer = context[SDWebImageContextImageTransformer];
    if (transformer) {
        key = [key stringByAppendingFormat:@"{%@}", [transformer transformerKey]];
    }

    return key;
}
@end
```

#### 3.2.2 缓存层级

```
┌──────────────────────────────────────────────────────────────────┐
│                      内存缓存（NSCache）                          │
│                                                                  │
│  key: "photo.jpg{w60_h60}"   → 60×60 解码后位图 (~14KB)         │
│  key: "photo.jpg{w375_h375}" → 375×375 解码后位图 (~562KB)      │
│  key: "photo.jpg"            → 原图解码后位图 (~48MB)            │
│                                                                  │
│  ⚠️ 内存缓存中同一 URL 不同尺寸各自独立存储                       │
│  ⚠️ 不同尺寸的内存占用差异巨大，必须分级管理                       │
├──────────────────────────────────────────────────────────────────┤
│                      磁盘缓存                                     │
│                                                                  │
│  key: "photo.jpg" → 原图数据（JPEG/WebP 压缩数据，~200KB）       │
│  key: "photo.jpg{w60_h60}" → 缩略图数据（~2KB）                 │
│  key: "photo.jpg{w375_h375}" → 中等尺寸数据（~20KB）            │
│                                                                  │
│  ⚠️ 磁盘存储压缩后的原始数据，占用远小于内存                      │
│  ⚠️ 可选择仅缓存原图数据，缩略图从原图降采样生成（省磁盘空间）    │
└──────────────────────────────────────────────────────────────────┘
```

### 3.3 降采样加载策略

#### 3.3.1 何时需要降采样

```
判断条件：
  图片原始尺寸 > targetSize * 2（屏幕缩放比 @2x/@3x 已计入 targetSize）
  则需要降采样

  示例（@2x 屏幕）：
  - UIImageView 尺寸 100×100 pt → targetSize = 200×200 pixel
  - 原图 4000×3000 pixel → 4000 > 200*2 → 需要降采样
  - 降采样后内存：200×200×4 = 160KB（vs 原图 48MB，减少 99.7%）
```

#### 3.3.2 降采样实现

```objc
// ✅ 正确的降采样方式：使用 CGImageSourceCreateThumbnailAtIndex
- (UIImage *)downsampleImageWithData:(NSData *)data
                           targetSize:(CGSize)targetSize {
    CGImageSourceRef source = CGImageSourceCreateWithData((__bridge CFDataRef)data, NULL);
    if (!source) return nil;

    // 获取原图尺寸
    CFDictionaryRef metadata = CGImageSourceCopyPropertiesAtIndex(source, 0, NULL);
    CGFloat originalWidth = [(NSNumber *)CFDictionaryGetValue(metadata, kCGImagePropertyPixelWidth) floatValue];
    CGFloat originalHeight = [(NSNumber *)CFDictionaryGetValue(metadata, kCGImagePropertyPixelHeight) floatValue];
    CFRelease(metadata);

    // 计算缩放比（取最大缩放比，确保图片至少一边匹配 targetSize）
    CGFloat scale = MAX(targetSize.width / originalWidth, targetSize.height / originalHeight);

    // 创建缩略图选项
    NSDictionary *options = @{
        (id)kCGImageSourceThumbnailMaxPixelSize : @(MAX(targetSize.width, targetSize.height)),
        (id)kCGImageSourceCreateThumbnailFromImageAlways : @YES,  // 即使原图比 targetSize 小也创建
        (id)kCGImageSourceShouldCacheImmediately : @YES,           // 立即解码，不在渲染时解码
        (id)kCGImageSourceCreateThumbnailWithTransform : @YES       // 保持方向
    };

    CGImageRef thumbnailRef = CGImageSourceCreateThumbnailAtIndex(source, 0, (__bridge CFDictionaryRef)options);
    CFRelease(source);

    if (!thumbnailRef) return nil;

    UIImage *result = [UIImage imageWithCGImage:thumbnailRef scale:UIScreen.mainScreen.scale orientation:UIImageOrientationUp];
    CGImageRelease(thumbnailRef);
    return result;
}
```

#### 3.4.1 缓存命中策略：从大图降采样 vs 重新下载

```objc
// 内存缓存查找顺序：
// 1. 精确尺寸匹配 → 直接返回（最快）
// 2. 更大尺寸命中 → 从大图降采样到目标尺寸（避免网络请求）
// 3. 无命中 → 查磁盘缓存

- (UIImage *)imageFromMemoryCacheForURL:(NSURL *)url targetSize:(CGSize)targetSize {
    // 第 1 步：精确尺寸匹配
    NSString *exactKey = [self cacheKeyForURL:url targetSize:targetSize];
    UIImage *exactImage = [self.memoryCache objectForKey:exactKey];
    if (exactImage) return exactImage;

    // 第 2 步：更大尺寸命中 → 降采样
    // 遍历内存缓存中同一 URL 的其他尺寸
    NSString *urlPrefix = url.absoluteString;
    NSArray *cachedKeys = [self.memoryCache allKeysForURLPrefix:urlPrefix];
    for (NSString *key in cachedKeys) {
        if ([key hasPrefix:urlPrefix] && [key containsString:@"{w"]) {
            CGSize cachedSize = [self sizeFromCacheKey:key];
            if (cachedSize.width >= targetSize.width && cachedSize.height >= targetSize.height) {
                UIImage *largerImage = [self.memoryCache objectForKey:key];
                return [self downsampleImage:largerImage toSize:targetSize];
            }
        }
    }

    return nil; // 无命中，查磁盘
}
```

## 四、销毁策略

图片加载库的销毁策略涉及内存缓存清理、任务取消、回调置空等多个方面，不当的销毁会导致**内存泄漏、OOM、野指针回调、列表卡顿**等严重问题。

### 4.1 需要销毁的资源清单

### 4.2 销毁时机

| 销毁时机 | 触发方式 | 销毁内容 | 保留内容 |
|---------|---------|---------|---------|
| UIImageView 移出屏幕 / cell 复用 | 滚动触发 | 取消该 View 对应的下载任务 | 全局缓存（其他 View 可能复用） |
| ViewController dealloc | 页面退出 | 取消该页面所有 View 的加载任务 | 全局缓存 |
| 收到内存警告 | 系统通知 | 清空 NSCache 内存缓存 + 弱缓存 | 磁盘缓存保留 |
| App 进入后台 | AppDelegate | 清空内存缓存（后台无需渲染） | 磁盘缓存保留 |
| 单例 Manager 手动销毁 | `invalidate` | 取消所有任务 + 清空所有缓存 | 无 |
| 磁盘缓存定期清理 | 定时器 / App 启动 | 超龄 / 超容量磁盘文件 | 最近使用的文件 |

### 4.3 销毁流程设计

```
  触发销毁
     │
     ▼
  ┌─ 第 1 步：取消进行中的加载任务 ─────────────────────┐
  │  遍历当前页面所有 UIImageView 的关联 operation       │
  │  调用 [operation cancel]                            │
  │  移除关联对象（objc_setAssociatedObject 移除）       │
  │  从全局任务字典中移除该任务                           │
  └───────────────────────────────────────────────────┘
     │
     ▼
  ┌─ 第 2 步：取消进行中的下载任务 ─────────────────────┐
  │  对 NSURLSessionDataTask 调用 [task cancel]         │
  │  清空 downloader 的 URL → [callback] 字典           │
  │  移除 NSOperationQueue 中待执行的下载 Operation      │
  └───────────────────────────────────────────────────┘
     │
     ▼
  ┌─ 第 3 步：取消进行中的解码任务 ─────────────────────┐
  │  解码在子线程的串行/并发队列中执行                    │
  │  取消解码 Operation（解码是耗时 CPU 操作）           │
  │  已开始解码的任务无法中断，但回调会被跳过              │
  └───────────────────────────────────────────────────┘
     │
     ▼
  ┌─ 第 4 步：置空所有回调 Block ──────────────────────┐
  │  将 completionBlock / progressBlock 设为 nil        │
  │  防止已取消的任务在完成时回调已释放的对象             │
  │  防止 UIImageView dealloc 后仍收到图片回调            │
  └───────────────────────────────────────────────────┘
     │
     ▼
  ┌─ 第 5 步：清理内存缓存 ────────────────────────────┐
  │  内存警告 / 后台场景：                               │
  │    [NSCache removeAllObjects]                       │
  │    清空弱引用辅助缓存 NSMapTable                      │
  │  页面退出场景：                                      │
  │    不清全局缓存（其他页面可能复用）                    │
  │    但大图/原图缓存应优先清理（内存占用最大）           │
  │  单例销毁场景：                                      │
  │    清空全部                                          │
  └───────────────────────────────────────────────────┘
     │
     ▼
  ┌─ 第 6 步：清理磁盘缓存（定期 / 手动）─────────────┐
  │  删除超过 maxAge 的文件                              │
  │  总大小超过 maxSize 时，按 LRU 删除最久未访问的文件   │
  │  删除同一 URL 的过时尺寸缓存（仅保留最近访问的尺寸） │
  │  后台线程执行，不阻塞主线程                           │
  └───────────────────────────────────────────────────┘
     │
     ▼
  销毁完成
```

### 4.4 各场景销毁实现

#### 4.4.1 UIImageView / cell 复用场景（最高频）

```objc
// SDWebImage 的核心：UIView+sdAssociatedObject
// 每个 UIImageView 通过关联对象绑定当前加载操作的 identifier

@implementation UIView (WebCache)

- (void)sd_setImageWithURL:(NSURL *)url placeholderImage:(UIImage *)placeholder {
    // 1. 先取消当前 View 上正在进行的加载任务
    [self sd_cancelCurrentImageLoad];

    // 2. 设置占位图
    self.image = placeholder;

    // 3. 创建新的加载操作
    if (url) {
        __weak typeof(self) weakSelf = self;
        SDWebImageOperation *operation = [SDWebImageManager.sharedManager loadImageWithURL:url
                                                                                     options:0
                                                                                     context:nil
                                                                                    progress:nil
                                                                                   completed:^(UIImage *image, NSError *error, SDImageCacheType cacheType, BOOL finished, NSURL *url) {
            __strong typeof(weakSelf) strongSelf = weakSelf;
            if (!strongSelf) return; // View 已销毁，不再设置图片

            // 4. 校验 URL 是否与当前 operationIdentifier 匹配
            //    防止 cell 复用导致旧回调覆盖新图片
            if ([strongSelf sd_imageOperationIdentifier] != operationIdentifier) {
                return; // 当前 View 已加载新 URL，旧回调丢弃
            }

            if (image) {
                strongSelf.image = image;
            }
        }];

        // 5. 将 operation 的 identifier 存入关联对象
        objc_setAssociatedObject(self, @selector(sd_imageOperationIdentifier), operation.identifier, OBJC_ASSOCIATION_RETAIN);
    }
}

- (void)sd_cancelCurrentImageLoad {
    // 获取当前关联的 operation identifier
    NSString *identifier = [self sd_imageOperationIdentifier];
    if (identifier) {
        // 从全局任务字典中找到对应 operation 并取消
        [SDWebImageManager.sharedManager cancelOperationWithIdentifier:identifier];
        // 移除关联对象
        objc_setAssociatedObject(self, @selector(sd_imageOperationIdentifier), nil, OBJC_ASSOCIATION_RETAIN);
    }
}
@end
```

#### 4.4.5 磁盘缓存定期清理

```objc
- (void)deleteOldFiles {
    dispatch_async(self.ioQueue, ^{
        NSDate *now = [NSDate date];
        NSMutableArray *filesToDelete = [NSMutableArray array];

        // 遍历磁盘缓存文件
        NSArray *cacheFiles = [self.fileManager contentsOfDirectoryAtPath:self.diskCachePath error:nil];
        for (NSString *fileName in cacheFiles) {
            NSString *filePath = [self.diskCachePath stringByAppendingPathComponent:fileName];
            NSDictionary *attrs = [self.fileManager attributesOfItemAtPath:filePath error:nil];

            // 超龄文件
            if ([attrs.fileModificationDate timeIntervalSinceDate:now] > self.config.maxDiskAge) {
                [filesToDelete addObject:filePath];
            }
        }

        // 删除超龄文件
        for (NSString *path in filesToDelete) {
            [self.fileManager removeItemAtPath:path error:nil];
        }

        // 超容量：按 LRU 删除
        NSUInteger totalSize = [self totalDiskSize];
        if (totalSize > self.config.maxDiskSize) {
            // 按最后修改时间排序，删除最旧的
            NSArray *sortedFiles = [cacheFiles sortedArrayUsingComparator:^NSComparisonResult(NSString *a, NSString *b) {
                NSDate *dateA = [self.fileManager attributesOfItemAtPath:a error:nil].fileModificationDate;
                NSDate *dateB = [self.fileManager attributesOfItemAtPath:b error:nil].fileModificationDate;
                return [dateA compare:dateB];
            }];

            for (NSString *fileName in sortedFiles) {
                NSString *filePath = [self.diskCachePath stringByAppendingPathComponent:fileName];
                [self.fileManager removeItemAtPath:filePath error:nil];
                totalSize -= [self.fileManager attributesOfItemAtPath:filePath error:nil].fileSize;
                if (totalSize < self.config.maxDiskSize * 0.7) break; // 清理到 70% 即止
            }
        }
    });
}
```

### 4.5 常见销毁问题与陷阱

#### 4.5.1 大图缓存导致 OOM

```
  场景：列表页加载 20 张图片，每张都缓存了原图位图
  内存：20 × 48MB = 960MB → OOM 崩溃！

  ✅ 解决方案：
  1. 列表只加载缩略图尺寸，不缓存原图位图
  2. NSCache 设置 totalCostLimit，按 cost 优先淘汰大图
  3. 大图使用 AutoClear 策略，用完即释放
  4. 内存警告时立即清空缓存
```

#### 4.5.2 UIImageView dealloc 后回调（野指针）

```
  图片下载完成 → 回调设置 self.image → 但 self (UIImageView) 已 dealloc → 崩溃！

  ✅ 解决方案（SDWebImage 的做法）：
  1. Block 中 __weak self，回调时检查 strongSelf 是否存在
  2. cell 复用时 sd_cancelCurrentImageLoad 取消旧任务
  3. 回调中校验 operationIdentifier 是否匹配当前 URL
  4. ViewController 退出时主动取消所有加载任务
```

#### 4.5.3 同一 URL 不同尺寸缓存互相覆盖

```
  ❌ 错误：缓存 key 只有 URL，不同尺寸共用同一 key
  缩略图 60×60 写入缓存 → 详情页加载 375×375 →
  命中了 60×60 的缓存 → 显示模糊缩略图！

  ✅ 正确：缓存 key 带尺寸后缀
  缩略图 key: "photo.jpg{w60_h60}"
  详情页 key: "photo.jpg{w375_h375}"
  两者独立缓存，互不干扰
```

#### 4.5.4 后台返回后图片消失

```
  App 进入后台 → 内存警告 → NSCache 清空所有缓存 →
  返回前台 → 所有图片需要重新加载（从磁盘缓存或网络）

  ✅ 优化：
  1. 后台清缓存时，保留弱引用辅助缓存（NSMapTable weak）
  2. 返回前台后，弱缓存可能仍有命中，减少重新加载
  3. 后台时不清磁盘缓存，前台时从磁盘缓存快速恢复
  4. 列表场景使用 prefetch（预加载下一页图片）
```

### 4.6 销毁策略最佳实践总结

1. **cell 复用时必须 `sd_cancelCurrentImageLoad`**，取消旧任务避免回调混乱
2. **回调中使用 `__weak self`**，防止 UIImageView dealloc 后野指针崩溃
3. **回调中校验 operationIdentifier**，防止旧回调覆盖新图片
4. **内存警告时立即清空 NSCache**，优先淘汰大图/原图
5. **NSCache 设置 `totalCostLimit`**，根据图片像素数计算 cost，自动按占用淘汰
6. **大图使用 `AutoClear` 策略**，用完立即从缓存移除，不长期持有
7. **后台时清空内存缓存但保留磁盘缓存**，前台恢复时可快速从磁盘重新加载
8. **磁盘缓存定期清理**，App 启动和进入后台时执行，删除超龄和超容量文件
9. **缓存 key 必须带尺寸后缀**，防止不同尺寸互相覆盖

## 五、缓存淘汰策略全解

图片加载库的缓存淘汰（Cache Eviction）策略决定**当缓存空间不足时，应该移除哪些数据**。一个设计良好的淘汰策略是图片加载库稳定运行的基石。

### 5.1 淘汰策略全景

| 策略 | 核心思想 | 淘汰依据 | 实现复杂度 | 内存缓存 | 磁盘缓存 | 说明 |
|------|---------|---------|-----------|---------|---------|------|
| **LRU** | 最近最少使用 | 最后访问时间 | 低 | ✅ NSCache 默认 | ✅ SDDiskCache 默认 | 最通用，局部性原理 |
| **LFU** | 最不经常使用 | 访问频率 | 中 | ❌ | ✅ 可自行实现 | 热点数据更准，但历史数据难衰减 |
| **FIFO** | 先进先出 | 添加时间 | 低 | ❌ | ✅ 可配置 | 最简单，但不考虑使用模式 |
| **TTL** | 生存时间 | 固定过期时间 | 低 | ❌ | ✅ SDDiskCache 支持 | 适合有明确生命周期的数据 |
| **Cost-based** | 基于成本 | 内存占用大小 | 中 | ✅ totalCostLimit | ❌ | 优先淘汰大图，内存友好 |
| **Count-based** | 基于数量 | 缓存项数量 | 低 | ✅ countLimit | ❌ | 简单限制条目数 |
| **2Q** | 双队列 | 访问模式（一次 vs 多次） | 高 | ❌ | ❌ | LRU 的改进版，解决"一次大量"污染 |
| **Adaptive** | 自适应 | 工作负载动态 | 极高 | ❌ | ❌ | 如 ARC（Adaptive Replacement Cache） |
| **Per-size Tier** | 按尺寸分级 | 图片尺寸等级 | 中 | ✅ 3.5 节实现 | ❌ | 大图少存，小图多存 |
| **NSCache 自动淘汰** | 系统内存压力 | 系统级低内存通知 | 低 | ✅ 系统自动 | ❌ | iOS 特有，无需手动干预 |
| **Weak Cache** | 弱引用保留 | 引用是否存在 | 低 | ✅ NSMapTable | ❌ | 不是主动淘汰，但辅助缓存命中 |
| **AutoClear** | 用完即清 | 使用标记 | 低 | ✅ 4.4.4 节 | ❌ | 原图/编辑图场景 |
| **GreedyDual** | 贪心双倍 | 成本 + 老化因子 | 高 | ❌ | ❌ | 适合大小不同的缓存项（如 Web 代理） |

### 5.2 LRU（Least Recently Used）— 使用最广泛

#### 5.2.1 原理

LRU 假设**最近被访问过的数据，未来也最有可能被再次访问**。淘汰时移除最久未被访问的条目。

```
访问顺序：A → B → C → D → E（缓存满）
再次访问 A → 将 A 移到最新位置
新访问 F → 缓存满 → 淘汰最久未使用的 B（因为 B 是唯一未被再次访问的）

缓存列表示意（最新 → 最旧）：
初始: [E, D, C, B, A]     ← 满，A 最旧
访问 A: [A, E, D, C, B]    ← A 移到最新，B 最旧
插入 F: [F, A, E, D, C]    ← 淘汰 B，F 最新
```

#### 5.2.2 NSCache 的 LRU 实现

NSCache 内部使用优化的 LRU 算法，不是最纯粹的 LRU（不保证每次淘汰绝对最佳），但性能更好：

```objc
// NSCache 的核心淘汰逻辑
// 1. 当 totalCost 超过 totalCostLimit → 按 cost 从大到小淘汰
// 2. 当 count 超过 countLimit → 按访问时间从旧到新淘汰
// 3. 系统内存警告 → 快速清空全部

@interface SDMemoryCache : NSCache
@property (nonatomic, assign) NSUInteger maxMemoryCost;   // 映射到 NSCache.totalCostLimit
@property (nonatomic, assign) NSUInteger maxMemoryCount;  // 映射到 NSCache.countLimit

- (void)setObject:(id)obj forKey:(id)key cost:(NSUInteger)g {
    // g 是成本值，通常用图片的像素数作为 cost
    // 大图（48MB）→ cost=48,000,000，小图（14KB）→ cost=14,000
    // 内存满时，NSCache 优先淘汰 cost 大的条目（大图先被淘汰）
    [super setObject:obj forKey:key cost:g];
}
@end
```

**为什么 NSCache 不保证严格 LRU？**
- NSCache 的实现是**近似 LRU**，不是严格 LRU
- 严格 LRU 需要双向链表 + 哈希表，每次访问要移动链表节点
- NSCache 使用更轻量的策略：结合 cost 和 count 阈值，在达到限制时批量清理
- 这种设计在性能和准确性之间取得了平衡

#### 5.2.3 严格 LRU 的实现（参考）

```objc
// 严格 LRU 缓存：双向链表 + 哈希表
@interface StrictLRUCache : NSObject

@property (nonatomic, assign) NSUInteger capacity;

// 双向链表节点
@interface LRUNode : NSObject
@property (nonatomic, strong) id key;
@property (nonatomic, strong) id value;
@property (nonatomic, weak) LRUNode *prev;
@property (nonatomic, weak) LRUNode *next;
@end

@interface StrictLRUCache ()
@property (nonatomic, strong) NSMutableDictionary *cache; // key → node 映射
@property (nonatomic, strong) LRUNode *head; // 头部 = 最新访问
@property (nonatomic, strong) LRUNode *tail; // 尾部 = 最久未访问
@end

@implementation StrictLRUCache

- (id)objectForKey:(id)key {
    LRUNode *node = self.cache[key];
    if (!node) return nil;

    // 将节点移到链表头部（表示最近使用）
    [self moveToHead:node];
    return node.value;
}

- (void)setObject:(id)value forKey:(id)key cost:(NSUInteger)cost {
    LRUNode *node = self.cache[key];
    if (node) {
        // key 已存在：更新值，移到头部
        node.value = value;
        [self moveToHead:node];
    } else {
        // key 不存在：创建新节点
        node = [LRUNode new];
        node.key = key;
        node.value = value;
        self.cache[key] = node;
        [self addToHead:node];

        // 超出容量 → 淘汰尾部节点（最久未使用）
        if (self.cache.count > self.capacity) {
            [self removeTail];
        }
    }
}

- (void)moveToHead:(LRUNode *)node {
    if (node == self.head) return;
    // 断开当前连接
    [self removeNode:node];
    // 插入到头部
    [self addToHead:node];
}

- (void)removeTail {
    LRUNode *tail = self.tail;
    if (!tail) return;
    [self.cache removeObjectForKey:tail.key];
    [self removeNode:tail];
}
@end
```

#### 5.2.4 LRU 的优缺点

| 优点 | 缺点 |
|------|------|
| 实现简单，广泛使用 | **一次大量访问**会污染缓存（如遍历所有历史记录） |
| 利用时间局部性（刚访问过的数据很可能马上又要访问） | 不反映**访问频率**（被访问 100 次的条目可能被访问 1 次的淘汰） |
| 性能可预测，O(1) 操作 | 对偶发性大量访问敏感 |
| 与大多数业务场景匹配 | 需要维护链表，有额外内存开销 |

### 5.3 LFU（Least Frequently Used）— 访问频率优先

#### 5.3.1 原理

LFU 淘汰**访问频率最低**的条目，保留热点数据。核心假设：被多次访问的数据比仅被访问一次的数据更有价值。

```
Items: A(访问 100 次), B(访问 50 次), C(访问 1 次), D(访问 10 次)
缓存满，需要淘汰 1 个 →
淘汰 C（访问频率最低，1 次）

即使 C 是最近刚访问过的，只要频率低，仍然被淘汰
```

#### 5.3.2 LFU 的实现

```objc
@interface LFUCache : NSObject

@property (nonatomic, assign) NSUInteger capacity;

@end

@interface LFUCache ()
@property (nonatomic, strong) NSMutableDictionary *cache;    // key → value
@property (nonatomic, strong) NSMutableDictionary *freqMap;  // key → 访问次数
@property (nonatomic, strong) NSMutableDictionary *freqBuckets; // 访问次数 → [keys]
@property (nonatomic, assign) NSUInteger minFreq; // 当前最小访问次数
@end

@implementation LFUCache

- (id)objectForKey:(id)key {
    id value = self.cache[key];
    if (!value) return nil;

    // 增加访问频率
    NSUInteger freq = [self.freqMap[key] unsignedIntegerValue];
    [self.freqMap setObject:@(freq + 1) forKey:key];

    // 从旧频率桶移除，加入新频率桶
    NSMutableArray *oldBucket = self.freqBuckets[@(freq)];
    [oldBucket removeObject:key];
    if (oldBucket.count == 0) {
        [self.freqBuckets removeObjectForKey:@(freq)];
        if (self.minFreq == freq) self.minFreq = freq + 1;
    }

    NSMutableArray *newBucket = self.freqBuckets[@(freq + 1)];
    if (!newBucket) {
        newBucket = [NSMutableArray array];
        self.freqBuckets[@(freq + 1)] = newBucket;
    }
    [newBucket addObject:key];

    return value;
}

- (void)setObject:(id)value forKey:(id)key {
    if (self.cache.count >= self.capacity && !self.cache[key]) {
        // 淘汰最小访问频率桶中的第一个 key
        NSMutableArray *minBucket = self.freqBuckets[@(self.minFreq)];
        id evictKey = minBucket.firstObject;
        [minBucket removeObjectAtIndex:0];
        [self.cache removeObjectForKey:evictKey];
        [self.freqMap removeObjectForKey:evictKey];
        if (minBucket.count == 0) {
            [self.freqBuckets removeObjectForKey:@(self.minFreq)];
        }
    }

    self.cache[key] = value;
    self.freqMap[key] = @(1);
    self.minFreq = 1;

    NSMutableArray *bucket = self.freqBuckets[@(1)];
    if (!bucket) {
        bucket = [NSMutableArray array];
        self.freqBuckets[@(1)] = bucket;
    }
    [bucket addObject:key];
}

@end
```

#### 5.3.3 LFU 的优缺点与使用场景

| 优点 | 缺点 |
|------|------|
| 保留真正的热点数据 | **频率衰减问题**：历史高频率条目会长期占据缓存，即使已不再需要 |
| 抵抗偶发性大量访问 | 实现比 LRU 复杂 |
| 适合长期稳定的访问模式 | 需要维护频率计数器，内存开销大 |
| — | 难以区分"近期高频"和"过去高频" |

**解决方案**：带时间衰减的 LFU（TinyLFU），定期将频率减半或归零，让新热点数据有机会进入缓存。

**在图片加载库中的应用**：LFU 适合 CDN 资源缓存（某些图片长期热点），但 LRU 通常更适合图片加载场景（用户的浏览行为通常是"最近滚过的图片"）。

### 5.4 FIFO（First In First Out）— 先进先出

#### 5.4.1 原理

FIFO 淘汰**最早进入缓存**的数据，不考虑访问频率或最后访问时间：

```
插入顺序：A(第1个) → B(第2个) → C(第3个) → D(第4个)
缓存满（容量=4），插入 E →
淘汰 A（最早进入的），即使 A 刚被访问过

缓存列表示意（按进入顺序）：
插入前: [A, B, C, D]
再次访问 A → 缓存不变（FIFO 不关心访问时间）
插入 E: [E, B, C, D]   ← 淘汰 A
```

#### 5.4.2 FIFO 的优缺点

| 优点 | 缺点 |
|------|------|
| 实现极其简单 | **完全忽略访问模式**，热门数据可能被淘汰 |
| 性能开销小（无需维护访问记录） | 即使 A 刚刚被访问过，有新的进来仍然淘汰 A |
| 实现 O(1) | 不适合大多数缓存场景 |

**在图片加载库中不适合作为主淘汰策略**。但在某些场景可用：
- 磁盘缓存中"最老的文件"批量清理（与 TTL 配合）
- 预加载队列的管理（先入先加载）

### 5.5 TTL（Time To Live）— 基于时间过期

#### 5.5.1 原理

每个缓存项有一个到期时间，过期后自动移除：

```objc
@interface TTLData : NSObject
@property (nonatomic, strong) id value;
@property (nonatomic, strong) NSDate *expirationDate; // 到期时间
@end

@interface TTLImageCache : NSObject
@property (nonatomic, strong) NSCache *cache;
@property (nonatomic, assign) NSTimeInterval defaultTTL; // 默认过期时间（秒）

- (void)setObject:(id)value forKey:(id)key ttl:(NSTimeInterval)ttl {
    TTLData *data = [TTLData new];
    data.value = value;
    data.expirationDate = [NSDate dateWithTimeIntervalSinceNow:ttl];
    [self.cache setObject:data forKey:key];
}

- (id)objectForKey:(id)key {
    TTLData *data = [self.cache objectForKey:key];
    if (!data) return nil;

    // 检查是否过期
    if ([data.expirationDate timeIntervalSinceNow] < 0) {
        [self.cache removeObjectForKey:key]; // 已过期
        return nil;
    }
    return data.value;
}
@end
```

#### 5.5.2 在图片加载库中的应用

TTL 在图片加载中有两个典型用法：

```objc
// 用法 1：磁盘缓存按文件修改时间判断（SDWebImage 做法）
- (void)deleteExpiredFiles {
    NSDate *now = [NSDate date];
    for (NSString *fileName in [self allCacheFiles]) {
        NSString *filePath = [self.diskCachePath stringByAppendingPathComponent:fileName];
        NSDictionary *attrs = [self.fileManager attributesOfItemAtPath:filePath error:nil];
        NSTimeInterval age = [now timeIntervalSinceDate:attrs.fileModificationDate];
        // 超过 maxDiskAge（默认 1 周）即删除
        if (age > self.config.maxDiskAge) {
            [self.fileManager removeItemAtPath:filePath error:nil];
        }
    }
}

// 用法 2：每个缓存项独立过期时间（逐 item TTL）
// 用户头像 → 缓存 1 小时（头像可能更新）
// 商品图片 → 缓存 24 小时（商品图不太会变）
// 广告图片 → 缓存 30 分钟（广告经常换）
[self setObject:avatar forKey:@"user_avatar" ttl:3600];          // 1小时
[self setObject:product forKey:@"product_image" ttl:86400];       // 24小时
[self setObject:ad forKey:@"ad_image" ttl:1800];                   // 30分钟
```

#### 5.5.3 惰性淘汰 vs 主动淘汰

| 淘汰方式 | 实现 | 优点 | 缺点 |
|---------|------|------|------|
| **惰性淘汰**（Lazy） | 访问时检查，过期就删 | 实现简单，无额外开销 | 过期数据可能长时间占用空间 |
| **主动淘汰**（Eager） | 定时器 / 事件触发批量清理 | 及时释放空间 | 有额外的定时器开销 |

```objc
// 惰性淘汰：访问时检查
- (id)objectForKey:(id)key {
    TTLData *data = [self.cache objectForKey:key];
    if (data && [data.expirationDate timeIntervalSinceNow] < 0) {
        [self.cache removeObjectForKey:key]; // 惰性删除
        return nil;
    }
    return data.value;
}

// 主动淘汰：定时清理
- (void)startPeriodicEviction {
    self.evictionTimer = [NSTimer scheduledTimerWithTimeInterval:300 // 每 5 分钟
                                                          target:self
                                                        selector:@selector(evictExpiredEntries)
                                                        userInfo:nil
                                                         repeats:YES];
}

- (void)evictExpiredEntries {
    // 遍历所有缓存项，删除过期的
    for (id key in [self.cache allKeys]) {
        [self objectForKey:key]; // 利用惰性淘汰逻辑清理
    }
}
```

**SDWebImage 的做法**：磁盘缓存使用**惰性 + 主动**混合策略：
- 惰性：每次从磁盘读取时检查文件修改时间（`fileModificationDate` + `maxDiskAge`）
- 主动：App 启动时、进入后台时执行批量清理（`deleteOldFiles`）
- 主动：达到 `maxDiskSize` 上限时，按修改时间排序，删除最旧的文件直到小于 `maxDiskSize * 0.7`

### 5.6 Cost-based 淘汰 — 按内存占用淘汰

#### 5.6.1 原理

每个缓存项分配一个**成本值（cost）**，当总成本超过上限时，按 cost 从大到小淘汰：

```objc
// 以图片像素数作为 cost
// 60×60 缩略图 → cost = 60 × 60 × 4 = 14,400
// 375×375 中等图 → cost = 375 × 375 × 4 = 562,500
// 4000×3000 原图 → cost = 4000 × 3000 × 4 = 48,000,000

// NSCache 原生支持 cost 管理
NSCache *cache = [[NSCache alloc] init];
cache.totalCostLimit = 100 * 1024 * 1024; // 最大总 cost = 100MB

// 存入图片时传入 cost
// 大图 48MB → cost=48,000,000，远超小图 14KB
// 内存不足时，NSCache 优先淘汰 cost 最大的条目
// → 大图先被淘汰，小图保留
[cache setObject:image forKey:key cost:pixelWidth * pixelHeight * 4];
```

#### 5.6.2 Cost-based 的图片缓存策略

```objc
// 根据图片尺寸动态设置不同的 cost 阈值
- (NSUInteger)memoryCostForImage:(UIImage *)image {
    // cost = 像素数 × bytesPerPixel
    return image.size.width * image.size.height * image.scale * image.scale * 4;
}

// 不同尺寸图片设置不同的缓存策略
- (void)cacheImage:(UIImage *)image forKey:(NSString *)key {
    NSUInteger cost = [self memoryCostForImage:image];

    if (cost > LARGE_IMAGE_THRESHOLD) {   // 大图/原图
        // 采用 AutoClear 策略：存入最小 cost，让缓存优先淘汰
        // 或者直接不写入内存缓存，仅存磁盘
        [self setCache:image forKey:key cost:cost
           withPolicy:SDImageCacheDiscardPolicyAutoClear];
    } else {                                // 缩略图/中等图
        // 正常缓存
        [self.memoryCache setObject:image forKey:key cost:cost];
    }
}
```

**为什么 NSCache 按 cost 淘汰比按 count 更好？**

假设 countLimit = 100：
- 100 张缩略图（14KB 每张）→ 总内存 1.4MB ✅ 完全合理
- 2 张原图（48MB 每张）+ 98 张缩略图 → 总内存 ~97MB ⚠️ 偏高
- 100 张原图（48MB 每张）→ 总内存 4.8GB ❌ OOM！

按 cost 淘汰（totalCostLimit = 100MB）：
- 100 张缩略图 → totalCost ≈ 1.4MB ✅ 全留下
- 存入一张原图（48MB）→ 超过 100MB 时，优先淘汰原图 ✅ 自动控制
- 不会出现 count 限制下的大图堆积 OOM

### 5.7 Count-based 淘汰 — 按数量淘汰

#### 5.7.1 原理

限制缓存中的最大条目数，超出时淘汰：

```objc
NSCache *cache = [[NSCache alloc] init];
cache.countLimit = 200; // 最多缓存 200 张图片

// 当第 201 张图片存入时，NSCache 自动淘汰最久未使用的条目
```

#### 5.7.2 使用场景

| 场景 | countLimit | 为什么 |
|------|-----------|--------|
| 列表缩略图 | 500-1000 | 一张 60×60 缩略图约 14KB，500 张仅 7MB |
| 详情页图片 | 50-100 | 详情页图片尺寸大，数量少 |
| 动图帧缓存 | 取决于帧数 | SDAnimatedImagePlayer 用 `maxBufferSize`（按字节）控制 |
| 预加载缓存 | 200-300 | 预加载池，控制并发预加载数量 |

### 5.8 2Q（Two Queue）— 双队列算法

#### 5.8.1 原理

2Q 将缓存分为两个队列，解决 LRU 的"一次大量访问污染"问题：

```
             ┌───────────────────────┐
新访问 →      │   Am 队列              │
             │  （仅存 key，不存 value）│ ← FIFO 队列，第一次访问的数据进入这里
             └───────────┬───────────┘
                         │ 再次访问（说明是热点数据）
                         ▼
             ┌───────────────────────┐
             │   A1 队列              │
             │  （存 key + value）     │ ← LRU 队列，真正缓存数据
             └───────────┬───────────┘
                         │
                         ▼
                     被淘汰（A1 中的最久未使用）
```

- **Am（Main FIFO Queue）**：第一次访问的条目进入这里，**只存 key，不存实际数据**（低成本）
- **A1（Main LRU Queue）**：如果在 Am 中再次被访问，说明是热点数据，**移动到 A1**
- 只有当条目进入 A1 后，才真正消耗缓存空间
- Am 只需很小的容量（如总容量的 25%），FIFO 淘汰

**效果**：某用户翻完 100 页内容，所有图片只在 Am 中走一遍，然后 FIFO 淘汰，不会污染真正的 A1 缓存。只有被重复访问的图片才进入 A1。

#### 5.8.2 2Q 的优缺点

| 优点 | 缺点 |
|------|------|
| 有效防止"一次大量访问"污染缓存 | 实现比 LRU 复杂 |
| 热点命中率高于 LRU | 增加内存开销（Am 额外存储 key） |
| 适合有周期性热点变化的场景 | 需要调优 Am/A1 的比例 |

**在图片加载库中的应用**：2Q 适合聊天类场景——用户快速翻阅大量消息中的图片时，LRU 会被污染，而 2Q 可以区分"只看过一次"和"反复查看"的图片。

### 5.9 Weak Cache（弱引用辅助缓存）

#### 5.9.1 原理

这不是严格意义上的淘汰策略，而是**二级缓存加速**手段。使用 `NSMapTable` 持有图片的弱引用：

```objc
@interface SDMemoryCacheWithWeakRef : NSObject
@property (nonatomic, strong) NSCache *strongCache;   // 强引用（LRU 淘汰）
@property (nonatomic, strong) NSMapTable *weakCache;   // 弱引用（NSMapTable, weak-to-weak）

- (id)objectForKey:(id)key {
    // 第 1 层：NSCache（强引用，LRU 淘汰）
    id value = [self.strongCache objectForKey:key];
    if (value) return value;

    // 第 2 层：弱引用缓存（无淘汰，但只有其他对象引用时才存在）
    value = [self.weakCache objectForKey:key];
    if (value) {
        // 弱缓存命中 → 恢复到 NSCache
        [self.strongCache setObject:value forKey:key cost:[self costFor:value]];
        return value;
    }

    return nil;
}
```

#### 5.9.2 弱引用缓存的工作原理

```
状态 1：图片 A 被 UIImageView 1 和 UIImageView 2 同时展示
  NSCache:      [A key → 强引用 A]
  weakCache:    [A key → 弱引用 A]
  引用计数 = 3（NSCache + UIImageView1 + UIImageView2）

状态 2：内存警告 → NSCache 清空
  NSCache:      [空]
  weakCache:    [A key → 弱引用 A]
  引用计数 = 2（UIImageView1 + UIImageView2）→ A 仍然存活

状态 3：UIImageView 1 和 2 移出屏幕，图片不再展示
  NSCache:      [空]
  weakCache:    [A key → 弱引用 A] → nil（因为没有强引用持有 A 了）
  引用计数 = 0 → A 被释放
```

**核心价值**：NSCache 清空后，如果图片仍被其他对象引用（如其他 UIImageView），弱引用缓存可以立刻命中，避免从磁盘重新读取和解码。

### 5.10 AutoClear（用完即清）

#### 5.10.1 原理

针对**一次性大图场景**，加载完成后挂载到 View 上，但 View 移出屏幕后立即释放，不进入缓存：

```objc
- (void)loadLargeImageWithURL:(NSURL *)url
                  forView:(UIImageView *)imageView
               completion:(void(^)(UIImage *image))completion {
    // 加载大图/原图
    [self loadImageWithURL:url completion:^(UIImage *image) {
        // 设置到 View 上
        imageView.image = image;
        completion(image);

        // ⚡ 关键：不写入内存缓存，用完即清
        // imageView.image = image 已经持有了图片
        // imageView 移出屏幕 → 引用计数归零 → 自动释放
        // 不需要额外代码清理
    }];
}

// 如果需要缓存，用 LowPriority 策略
- (void)cacheLargeImageWithLowPriority:(UIImage *)image forKey:(NSString *)key {
    // 将大图以极小的 cost 存入缓存
    // 实际 cost 很小，在 totalCostLimit 限制下被优先淘汰
    NSUInteger fakeCost = 1; // 不按真实内存设置 cost
    [self.memoryCache setObject:image forKey:key cost:fakeCost];
}
```

#### 5.10.2 适用场景

| 场景 | 策略 | 原因 |
|------|------|------|
| 编辑页原图（48MB） | ✅ AutoClear | 只在编辑时使用，编辑完成即释放 |
| 全屏浏览大图（10MB） | ✅ AutoClear | 放大缩小用 CATiledLayer，不需要缓存位图 |
| 详情页头图（1-3MB） | ⚠️ LowPriority | 离开详情页后可保留，但优先淘汰 |
| 列表缩略图（14KB） | ❌ 正常缓存 | 很小，留缓存的收益高 |

#### 5.11.1 SDWebImage 的混合策略

SDWebImage 不只用一种策略，而是**混合多种**：

```
┌─────────────────────────────────────────────────────────────────┐
│                   SDWebImage 缓存淘汰体系                        │
│                                                                 │
│  内存缓存：                                                      │
│    NSCache（LRU ≈ + Cost-based + Count-based + 系统自动清理）    │
```

### 5.12 淘汰策略的选择指南

```
┌─────────────────────────────────────────────────────────────┐
│              根据业务场景选择淘汰策略                          │
│                                                             │
│  图片浏览 / 内容消费类 App（小红书、Instagram）：              │
│    - 内存：LRU + Cost-based（NSCache 默认） ✅ 推荐          │
│    - 磁盘：TTL + Size-based LRU ✅ 推荐                      │

│                                                             │
│  聊天 / 即时通讯类 App（微信、WhatsApp）：                     │
│    - 内存：2Q 或 Adaptive（防止大量消息图只读一次就污染缓存）    │
│    - 磁盘：TTL（消息图片有明确的时效性）                        │
│    - 原因：聊天翻看大量历史消息，一次遍历不应用污染缓存           │
│                                                             │
│  电商 / 商品详情类 App（淘宝、京东）：                          │
│    - 内存：LRU + 大图 AutoClear                              │
│    - 磁盘：TTL（商品图可能更新，不能缓存太久）                   │
│    - 原因：商品图片可能更新（规格/价格/活动），需要 TTL 控制      │
│                                                             │
│  工具类 / 文件扫描类 App（扫描王、文档阅读）：                    │
│    - 内存：AutoClear + Count-based                           │
│    - 磁盘：FIFO + TTL（文档扫描结果敏感，自动过期）              │

└─────────────────────────────────────────────────────────────┘
```

## 七、性能优化点

### 7.1 内存优化

1. **降采样**：大图只解码所需尺寸，内存占用从 `width * height * 4 bytes` 降为 `targetW * targetH * 4 bytes`
2. **子线程解码**：避免主线程隐式解码导致卡顿
3. **内存警告处理**：监听 `UIApplicationDidReceiveMemoryWarningNotification`，清理内存缓存
4. **弱引用二级缓存**：NSCache 释放后仍有机会通过弱引用命中

### 7.2 IO 优化

1. **异步磁盘读取**：磁盘 I/O 放到子线程，避免阻塞主线程
2. **IO 串行队列**：磁盘读写操作放入串行队列，保证数据安全的同时避免锁开销
3. **缓存命中统计**：记录缓存命中率，动态调整缓存策略

### 7.3 网络优化

1. **请求去重**：同一 URL 只发一次请求，多个回调共享数据
2. **断点续传**：大图下载支持断点续传
3. **HTTP/2 多路复用**：利用 NSURLSession 的 HTTP/2 支持
4. **COOP 编码**：支持 WebP/HEIC 等高压缩比格式

## 九、关键面试题

1. **SDWebImage 的缓存策略？**
   - 三级缓存：弱引用缓存 → NSCache（内存） → 磁盘缓存
   - 读取顺序：内存 → 磁盘 → 网络
   - 写入时机：下载完成后写磁盘，解码后写内存

2. **为什么用 NSCache 而不用 NSDictionary？**
   - NSCache 线程安全，无需加锁
   - 系统内存不足时自动清理
   - 不遵循 NSCopying 协议，key 不会被 copy，性能更好

3. **如何避免大图 OOM？**
   - 降采样：只解码目标尺寸
   - 使用 `CGImageSourceCreateThumbnailAtIndex` 而非全量解码
   - 异步逐行渲染（如 YYAsyncLayer）

4. **图片解码为什么要在子线程？**
   - UIImageView 赋值 image 时，若图片未解码，Core Animation 会在主线程解码
   - 主线程解码耗时会导致掉帧
   - 提前在子线程解码为位图，主线程只需渲染

5. **SDWebImage 如何保证 UI 不混乱？**
   - 通过 `UIView+sdAssociatedObject` 为每个 View 绑定一个 operationIdentifier
   - cell 复用时，先 cancel 上一个请求，再发起新请求
   - completion 回调中校验 URL 是否与当前 operationIdentifier 匹配

6. **不同尺寸的图片加载策略？**
   - 缓存 key 带 `{w60_h60}` 尺寸后缀，不同尺寸独立缓存互不干扰
   - 降采样：使用 `CGImageSourceCreateThumbnailAtIndex`，只解码目标尺寸，避免全量解码 OOM
   - 分级加载：缩略图（<200px）、中等尺寸（200-800px）、大图（>800px）、原图，各有不同的内存预算
   - 缓存命中时优先从更大尺寸降采样，避免重复下载
   - CDN 图片裁剪：拼接 `x-oss-process=image/resize,w_60,h_60` 参数，服务端裁剪

7. **图片加载库的销毁策略？**
   - cell 复用：`sd_cancelCurrentImageLoad` 取消旧任务 + 校验 operationIdentifier
   - 内存警告：清空 NSCache + 弱缓存，优先淘汰大图/原图
   - App 后台：清空内存缓存保留磁盘缓存，前台从磁盘恢复
   - 大图专项：AutoClear 策略，48MB 原图用完即释放
   - 磁盘清理：App 启动/后台时定期清理超龄、超容量文件
   - 回调守卫：`__weak self` + operationIdentifier 校验，防止 dealloc 后野指针崩溃
