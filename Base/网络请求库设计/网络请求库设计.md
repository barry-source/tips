### 2.3 安全层

#### 2.3.1 SSL Pinning（证书绑定）

```
┌──────────────────────────────────────────────────────────┐
│                   AFSecurityPolicy                        │
│                                                          │
│  AFSSLPinningModeNone:       不做证书校验（默认）           │
│  AFSSLPinningModePublicKey:  校验公钥（推荐）              │
│  AFSSLPinningModeCertificate: 校验证书                    │
│                                                          │
│  allowInvalidCertificates:   是否允许自签名证书            │
│  validatesDomainName:        是否校验域名                  │
│  pinnedCertificates:         绑定的证书集合                │
└──────────────────────────────────────────────────────────┘
```

- **公钥校验（推荐）**：只比对服务器证书公钥与本地公钥是否一致，证书轮换时无需更新 App
- **证书校验**：比对整个证书，更严格但证书过期需更新 App
- **域名校验**：检查证书的 Common Name / Subject Alternative Name 是否匹配请求域名

```objc
// 配置 SSL Pinning
AFSecurityPolicy *policy = [AFSecurityPolicy policyWithPinningMode:AFSSLPinningModePublicKey];
policy.allowInvalidCertificates = NO;
policy.validatesDomainName = YES;

// 加载本地证书
NSString *cerPath = [[NSBundle mainBundle] pathForResource:@"server" ofType:@"cer"];
NSData *cerData = [NSData dataWithContentsOfFile:cerPath];
policy.pinnedCertificates = [NSSet setWithObject:cerData];

manager.securityPolicy = policy;
```

## 三、销毁策略

网络请求库的销毁策略是整个设计中极其重要的一环，不当的销毁会导致**内存泄漏、野指针回调、无效请求浪费带宽**等问题。

### 3.1 需要销毁的资源清单

```
┌──────────────────────────────────────────────────────────────┐
│                    网络请求库持有的资源                         │
│                                                              │
│  ┌────────────────┐  ┌────────────────┐  ┌────────────────┐ │
│  │ NSURLSession   │  │ 进行中的 Task   │  │ 回调 Block     │ │
│  │ (连接池/缓存)  │  │ (DataTask /    │  │ (success /     │ │
│  │                │  │  UploadTask /  │  │  failure /      │ │
│  │                │  │  DownloadTask) │  │  progress)      │ │
│  └────────────────┘  └────────────────┘  └────────────────┘ │
│                                                              │
│  ┌────────────────┐  ┌────────────────┐  ┌────────────────┐ │
│  │ Reachability   │  │ 请求队列       │  │ 拦截器链       │ │
│  │ 监控          │  │ (OperationQueue│  │ (Interceptors) │ │
│  │                │  │  / 自定义队列) │  │                │ │
│  └────────────────┘  └────────────────┘  └────────────────┘ │
│                                                              │
│  ┌────────────────┐  ┌────────────────┐                     │
│  │ DNS 缓存       │  │ Token 刷新锁   │                     │
│  │ (预解析结果)   │  │ (并发控制)     │                     │
│  └────────────────┘  └────────────────┘                     │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 销毁时机

| 销毁时机 | 触发方式 | 说明 |
|---------|---------|------|
| ViewController dealloc | 自动触发 | 页面退出时，释放该页面关联的请求 |
| 单例 Manager 手动销毁 | `invalidate` 方法 | App 退出或模块卸载时 |
| 模块切换 | 业务触发 | 如切换账号时清理旧请求 |
| 内存警告 | 系统通知 | 释放非必要请求和缓存 |
| App 进入后台 | AppDelegate 触发 | 可选择性取消非关键请求 |

### 3.3 销毁流程设计

```
  触发销毁
     │
     ▼
  ┌─ 第 1 步：取消所有进行中的请求 ─────────────────────┐
  │  遍历 tasks 字典，对每个 NSURLSessionTask 调用      │
  │  [task cancel]                                      │
  │  清空 tasks 字典                                    │
  │  清空请求队列中的待执行 Operation                    │
  └────────────────────────────────────────────────────┘
     │
     ▼
  ┌─ 第 2 步：置空所有回调 Block ───────────────────────┐
  │  将所有 completionBlock / progressBlock 设为 nil    │
  │  避免已取消的 Task 回调时访问已释放的对象             │
  │  关键：防止野指针 / dealloc 后回调                   │
  └────────────────────────────────────────────────────┘
     │
     ▼
  ┌─ 第 3 步：销毁 NSURLSession ───────────────────────┐
  │  调用 [session invalidateAndCancel]                 │
  │  此操作会：                                         │
  │    - 取消所有未完成的 Task                           │
  │    - 释放 Session 持有的连接池                       │
  │    - 清除 Session 的 delegate 引用                   │
  │  注意：一旦 invalidate，Session 不可再使用           │
  └────────────────────────────────────────────────────┘
     │
     ▼
  ┌─ 第 4 步：停止网络监控 ─────────────────────────────┐
  │  调用 [reachabilityManager stopMonitoring]           │
  │  释放 SCNetworkReachabilityRef                      │
  │  移除 Reachability 回调                              │
  └────────────────────────────────────────────────────┘
     │
     ▼
  ┌─ 第 5 步：清理辅助资源 ─────────────────────────────┐
  │  清空请求去重字典                                    │
  │  释放 Token 刷新锁                                   │
  │  清空拦截器链                                        │
  │  释放 DNS 缓存                                       │
  │  移除通知观察者（内存警告等）                          │
  └────────────────────────────────────────────────────┘
     │
     ▼
  销毁完成，所有资源已释放
```

### 3.4 核心销毁代码实现

#### 3.4.1 ViewController 级别销毁（最常见场景）

```objc
@interface MyViewController : UIViewController
@property (nonatomic, strong) NSMutableArray<NSURLSessionDataTask *> *pendingTasks;
@end

@implementation MyViewController

// 发起请求时记录 Task
- (void)fetchData {
    NSURLSessionDataTask *task = [manager GET:url parameters:params success:^(...) {
        // 回调中检查 self 是否已销毁
        if (!self) return;
        // 处理数据
    } failure:^(...) {
        if (!self) return;
        // 处理错误
    }];
    [self.pendingTasks addObject:task];
}

// ❌ 错误做法：依赖 dealloc 回调 Block（Block 可能持有 self 导致循环引用）
// dealloc 无法执行，因为 Block → self → pendingTasks → Task → Block

// ✅ 正确做法：在 viewWillDisappear 或 willMoveToParentViewController 中主动取消
- (void)viewWillDisappear:(BOOL)animated {
    [super viewWillDisappear:animated];
    [self cancelAllPendingRequests];
}

- (void)cancelAllPendingRequests {
    for (NSURLSessionDataTask *task in self.pendingTasks) {
        [task cancel];
    }
    [self.pendingTasks removeAllObjects];
    // 置空 Block 防止延迟回调
}

- (void)dealloc {
    // 兜底：确保所有请求已取消
    [self cancelAllPendingRequests];
    NSLog(@"ViewController 已销毁，无残留请求");
}
@end
```

#### 3.4.2 Manager 级别销毁

```objc
@interface AFHTTPSessionManager : NSObject

// ✅ 完整销毁方法
- (void)invalidateSessionCancelingTasks:(BOOL)cancelPendingTasks {
    // 第 1 步：取消进行中的请求
    if (cancelPendingTasks) {
        [self.session getTasksWithCompletionHandler:^(NSArray *dataTasks, NSArray *uploadTasks, NSArray *downloadTasks) {
            for (NSURLSessionTask *task in dataTasks) { [task cancel]; }
            for (NSURLSessionTask *task in uploadTasks) { [task cancel]; }
            for (NSURLSessionTask *task in downloadTasks) { [task cancel]; }
        }];
    }

    // 第 2 步：销毁 Session（同时取消 Task + 释放连接池 + 清除 delegate）
    // invalidateAndCancel = invalidate + cancel all tasks
    // finishTasksAndInvalidate = 完成已进行的 Task 再销毁（不取消）
    if (cancelPendingTasks) {
        [self.session invalidateAndCancel];
    } else {
        [self.session finishTasksAndInvalidate];
    }

    // 第 3 步：停止网络监控
    [self.reachabilityManager stopMonitoring];

    // 第 4 步：清理辅助资源
    [self.taskDictionary removeAllObjects];
    [self.requestDeduplicator removeAllRequests];
    [self.interceptors removeAllObjects];
}

// ❌ 错误：只置 nil 不 invalidate
- (void)wrongDestroy {
    self.session = nil; // Session 内部线程仍在运行，delegate 回调可能访问已释放对象
}

@end
```

#### 3.4.3 Swift 版本销毁

```swift
class NetworkManager {
    private let session: URLSession
    private var pendingTasks: [URLSessionDataTask] = []

    // ✅ 完整销毁
    func invalidate() {
        // 取消所有进行中的请求
        pendingTasks.forEach { $0.cancel() }
        pendingTasks.removeAll()

        // 销毁 Session
        session.invalidateAndCancel()

        // 停止网络监控
        reachability.stopMonitoring()
    }

    deinit {
        invalidate()
        print("NetworkManager 已销毁")
    }
}

// ✅ ViewController 级别销毁
class MyViewController: UIViewController {
    private var requests: [Cancellable] = []  // Cancellable 协议封装

    override func viewWillDisappear(_ animated: Bool) {
        super.viewWillDisappear(animated)
        requests.forEach { $0.cancel() }
        requests.removeAll()
    }
}
```

### 3.5 常见销毁问题与陷阱

#### 3.5.1 循环引用导致无法销毁

```
  Block → self (strong) → pendingTasks → Task → Session → delegate → Block
                    ↑_______________________________________________↓
                              循环引用！
```

**解决方案**：

```objc
// ✅ 使用 weak self 打破循环
[manager GET:url parameters:params success:^(NSURLSessionDataTask *task, id responseObject) {
    __weak typeof(self) weakSelf = self;
    [weakSelf handleSuccess:responseObject];
} failure:^(NSURLSessionDataTask *task, NSError *error) {
    __weak typeof(self) weakSelf = self;
    [weakSelf handleFailure:error];
}];
```

#### 3.5.2 Session invalidate 后仍被使用

```objc
// ❌ 错误：invalidate 后继续发请求
[manager invalidateSessionCancelingTasks:YES];
[manager GET:url ...]; // Session 已失效，请求无法发出，但不会报错

// ✅ 正确：销毁后重建或阻止
- (NSURLSessionDataTask *)GET:(NSString *)URLString ... {
    if (self.isInvalidated) {
        if (failure) {
            NSError *error = [NSError errorWithDomain:@"NetworkManager"
                                                 code:-1
                                             userInfo:@{NSLocalizedDescriptionKey: @"Manager 已销毁"}];
            failure(nil, error);
        }
        return nil;
    }
    // 正常请求流程
}
```

#### 3.5.3 dealloc 后回调（野指针）

```
  请求已发出 → ViewController dealloc → Task 仍在执行
       → Task 完成 → Session 回调 delegate → delegate 已释放 → 崩溃！
```

**解决方案**：

1. **主动取消**：在 `viewWillDisappear` 中取消所有请求（推荐）
2. **delegate 弱引用**：Session delegate 对 Manager 持有 weak 引用
3. **回调守卫**：Block 中检查 `self` 是否为 nil

```objc
// ✅ 方案 1：主动取消（最可靠）
- (void)viewWillDisappear:(BOOL)animated {
    [super viewWillDisappear:animated];
    for (NSURLSessionDataTask *task in self.pendingTasks) {
        [task cancel];
    }
    [self.pendingTasks removeAllObjects];
}

// ✅ 方案 2：Session delegate 使用弱引用
@interface AFHTTPSessionManager : NSObject <NSURLSessionDelegate>
// Manager 是 Session 的 delegate，如果 Session 强引用 Manager 会循环引用
// NSURLSession 的 delegate 是强引用！所以需要中间对象
@end

// AFNetworking 的解决方案：使用 _AFURLSessionManagerWritingTask 代理
// Session delegate → 中间对象（弱引用 Manager）→ Manager
```

#### 3.5.4 网络监控未停止

```objc
// ❌ 错误：Reachability 的 SCNetworkReachabilityRef 未释放
// deinit 中忘记 stopMonitoring，导致 C 函数回调访问已释放对象 → 崩溃

// ✅ 正确：deinit 中必须停止监控
- (void)dealloc {
    [self.reachabilityManager stopMonitoring]; // 释放 SCNetworkReachabilityRef
}
```

### 3.6 销毁策略对比

| 策略 | 适用场景 | 行为 | 风险 |
|------|---------|------|------|
| `invalidateAndCancel` | 页面退出 / 模块卸载 | 立即取消所有 Task + 销毁 Session | 无延迟回调风险 |
| `finishTasksAndInvalidate` | App 优雅退出 | 等待已发出的请求完成再销毁 | 回调可能访问已释放对象 |
| 仅 cancel Task 不 invalidate | 临时暂停 | 取消请求但保留 Session | Session 可复用，但需管理回调 |
| 仅置 nil Session | ❌ 不推荐 | Session 内部线程仍在运行 | **内存泄漏 + 野指针崩溃** |

### 3.7 最佳实践总结

1. **ViewController 退出时主动取消所有请求**，不要依赖 dealloc（循环引用可能导致 dealloc 不执行）
2. **Manager 销毁时使用 `invalidateAndCancel`**，一次性清理 Session + Task + 连接池
3. **Block 中使用 `__weak self`**，防止循环引用和 dealloc 后回调
4. **Session invalidate 后标记状态**，阻止后续请求并返回错误
5. **Reachability 必须在 dealloc 中 stopMonitoring**，否则 C 回调访问已释放对象会崩溃
6. **内存警告时取消非关键请求**，释放带宽和内存

## 四、常见问题与解决方案

### 4.1 Token 过期自动刷新

```
  请求 A（Token 过期，返回 401）
        │
        ▼
  拦截 401 → 暂停 A → 发送 Token 刷新请求
        │
        ▼
  刷新成功 → 用新 Token 重发 A
  刷新失败 → 回调 A 失败，跳转登录页
        │
        ▼
  如果同时有 B、C 也收到 401：
  只发一次刷新请求，B、C 等待刷新完成后一起重试
```

## 六、性能优化

### 6.1 连接复用

- `NSURLSession` 内部维护连接池，相同 host 复用 TCP 连接
- 设置 `HTTPShouldUsePipelining = YES` 启用 HTTP 管道化
- HTTP/2 多路复用，一个 TCP 连接并行多个请求

### 6.2 请求优化

1. **请求合并**：多个小请求合并为一个批量接口
2. **数据压缩**：请求头添加 `Accept-Encoding: gzip, deflate`
3. **缓存策略**：合理使用 ETag / Last-Modified / If-None-Match
4. **DNS 预解析**：提前解析域名，减少首次连接耗时
5. **请求优先级**：关键接口设置高优先级，非关键接口低优先级

### 6.3 弱网优化

1. **超时策略**：弱网环境适当增大超时时间
2. **数据缓存**：离线模式使用本地缓存数据
3. **增量同步**：仅同步变更数据，减少传输量
4. **压缩传输**：Protobuf 替代 JSON，体积减少 30%-50%
5. **断点续传**：大文件下载支持 Range 请求

## 七、关键面试题

1. **AFNetworking 底层实现？**
   - 基于 NSURLSession 封装，提供更友好的 API
   - AFHTTPSessionManager 管理 Session、序列化器、安全策略
   - 通过 NSURLSessionDataTask 执行实际的网络请求

2. **AFN 2.x 和 3.x 的区别？**
   - 2.x 使用 NSURLConnection + NSOperation，有常驻线程处理回调
   - 3.x 使用 NSURLSession，系统管理回调线程，移除了常驻线程
   - 3.x 不再需要 AFHTTPRequestOperation

3. **如何做请求签名？**
   - 将请求参数按 key 排序拼接
   - 加上时间戳和随机串防重放
   - 使用 HMAC-SHA256 加密生成签名
   - 签名放入请求头

4. **如何防止中间人攻击？**
   - SSL Pinning（证书绑定 / 公钥绑定）
   - 证书校验 + 域名校验
   - 请求签名 + 数据加密
   - 不信任用户安装的自定义证书

5. **网络请求的线程模型？**
   - NSURLSession 是线程安全的，可在任意线程创建和使用
   - 回调在 delegateQueue 中执行（默认串行队列）
   - completionBlock 默认在主线程回调
   - 自定义 serialQueue 可控制回调线程

6. **网络请求库的销毁策略？**
   - 资源清单：Session、进行中的 Task、回调 Block、Reachability、拦截器链
   - 销毁流程：取消 Task → 置空 Block → invalidate Session → 停止监控 → 清理辅助资源
   - `invalidateAndCancel` vs `finishTasksAndInvalidate`：前者立即取消所有请求，后者等请求完成再销毁
   - ViewController 退出时主动取消请求，不要依赖 dealloc（循环引用可能阻止 dealloc 执行）
   - Session 的 delegate 是强引用，需中间对象打破循环（AFNetworking 使用 _AFURLSessionManagerWritingTask）

7. **dealloc 后网络回调导致崩溃怎么解决？**
   - 根因：Task 完成后回调已释放的 delegate/Block → 野指针崩溃
   - 方案 1（推荐）：viewWillDisappear 主动取消所有请求
   - 方案 2：Block 中使用 `__weak self`，回调时检查 self 是否为 nil
   - 方案 3：Session delegate 使用中间对象，弱引用 Manager
   - Reachability 的 C 回调同理，必须在 dealloc 中 stopMonitoring
